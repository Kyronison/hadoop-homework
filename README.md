# Hadoop: HDFS и YARN

Домашние задания по развёртыванию Hadoop на четырёх виртуальных машинах.

Статус проверки: HDFS и YARN работают; все 11 веб-интерфейсов проверены с внешнего компьютера через SSH на localhost. Этот способ доступа используется для ДЗ2. Дополнительный HTTPS-прокси проверен только внутри стенда; его публикация в Интернет для выполнения задания не требуется. Подробности и границы проверки — в [VALIDATION.md](VALIDATION.md).

- [ДЗ1 — HDFS](hw1/README.md): NameNode, SecondaryNameNode и три DataNode.
- [ДЗ2 — YARN](hw2/README.md): ResourceManager, три NodeManager, JobHistory, Web Application Proxy и доступ к веб-интерфейсам через SSH с открытием на localhost.
- [Результаты проверки](VALIDATION.md): запуск на учебном стенде и результат WordCount.

Используются Ubuntu 24.04, Java 11, Python 3.12 и Hadoop 3.4.2. Python-скрипты работают без сторонних библиотек.

## Схема кластера

| Роль | Сервисы |
|---|---|
| master | NameNode, ResourceManager, JobHistory, Web Application Proxy |
| worker1 / edge | DataNode, NodeManager, SecondaryNameNode; запуск установки |
| worker2 | DataNode, NodeManager |
| worker3 | DataNode, NodeManager |

Третий DataNode размещён на edge: вместе с двумя выделенными рабочими ВМ получается три узла хранения. SecondaryNameNode делает контрольные точки метаданных, но не заменяет NameNode при аварии.

На edge работают три постоянных JVM: DataNode, NodeManager и SecondaryNameNode. Для каждой установлен максимальный heap 512 MiB; YARN дополнительно выделяет до 1536 MiB контейнерам. На ВМ с 3886 MiB остаётся около 814 MiB сверх этих лимитов heap и контейнеров на ОС и дополнительную память JVM. Это учебная конфигурация для небольшой нагрузки; при её увеличении нужно уменьшить ресурс YARN или увеличить память ВМ. Проверка установки требует не менее `yarn_memory_mb + 1800` MiB, но не заменяет наблюдение за фактической памятью.

## Настройки

Скопировать пример и заполнить параметры своего стенда:

```bash
cp inventory.example.json inventory.json
```

В примере указаны условные имена и адреса. Нужно заменить `ssh_host` на фактическое короткое имя каждой ВМ, а `private_ip` — на её внутренний IPv4. Короткие и канонические имена всех четырёх ВМ должны разрешаться в соответствующие внутренние IP с каждого узла, включая master. Обратное разрешение IP должно возвращать имя, которое разрешается обратно в тот же IP. Это обеспечивается DNS или согласованными записями `/etc/hosts`; [предварительная проверка ДЗ1](hw1/README.md#подготовка) ничего в них не меняет. Порядок ролей: `master`, `worker1`, `worker2`, `worker3`.

`ssh_key` — путь к ключу для внутренних ВМ на edge. Сам ключ не копируется. `local: true` у worker1 означает, что этот узел — машина, на которой запускается установка; её hostname должен совпадать с `ssh_host`. Для внешнего подключения к edge используется отдельный локальный ключ.

В проверенной конфигурации у каждой ВМ было 4 ГБ RAM и 2 vCPU. Для YARN выделено по 1536 MiB и 2 vcores на worker. Все данные находятся в выделенном каталоге `install_root`, например `/home/team/teachbase-hadoop`.

Далее выполнить подготовку и установку по инструкциям [ДЗ1](hw1/README.md), затем [ДЗ2](hw2/README.md). Для работы нужны папки `common`, `hw1`, `hw2` из одного репозитория.

## Проверка скриптов

```bash
python3 -m unittest discover -s tests -v
python3 -m compileall -q common hw1 hw2 tests
bash -n common/node.sh
python3 common/cluster.py render --inventory inventory.example.json --output generated-example
```

Эти команды не подключаются к ВМ. Тесты проверяют XML, состав кластера, распознавание неисправных узлов, запуск демонов и отказ от форматирования непустого каталога. Для Bash-тестов нужен обычный пользователь; на Windows используется Git Bash.

При запуске от root пять Bash-тестов пропускаются: итог unittest содержит `skipped=5`, даже если остальные тесты прошли. Без Bash они также пропускаются. Для полной проверки запустить тесты от обычного пользователя с установленным Bash и проверить, что итог не содержит пропусков.

Реальные настройки, ключи и полные журналы не входят в репозиторий. Краткие результаты запуска приведены в [VALIDATION.md](VALIDATION.md), исходные числовые показатели — в [checks/results.json](checks/results.json).
